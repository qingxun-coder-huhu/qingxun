# 需求描述编写指南

这份指南讲的是**你在「生成脚本」页面需求框里输入的那段话**该怎么写。

你的描述是整条流水线唯一的输入：它同时决定了模型生成什么脚本、调试时模拟设备回放什么报文、
以及评估环节按什么标准判定通过。描述里没写的，平台不会替你假设——脚本被明令禁止编造数据，
评估会把它判成"信息不足"，然后把问题抛回来让你确认。所以**描述写得越具体，一次跑通的概率越高**。

---

## 一句话原则

把需求写成一份清单：**每一条 = 命令 + 真实回显 + 处理逻辑 + 预期**，
而不是写一个目标（"检查设备是否正常"）。

原因很直接：评估环节是**按条目逐条核对**的。需求里每一个"可验证的操作或判定"算一条
（下发某命令、回显含某内容、数值低于某阈值、记录某字段），每条都必须能找到证据。
你写成一个笼统目标，评估就只能给一条笼统结论，个别失败会被整体印象淹没；
而且失败之后模型不知道该改哪一条。

---

## 必须写清楚的五件事

### 1. 命令——逐字写

写命令的完整原文，不要写"查看版本"这种转述。命令是脚本 `connection.cli(...)` 里逐字下发的
内容，也是模拟设备命令映射的键；对不上就会返回 `Command 'xxx' not recognized.`。

### 2. 真实回显——原文照抄，禁止省略，但剥掉系统提示符

回显原文是模拟调试环境**实际回放**的报文，脚本的正则会照着它写。所以：

- 保留原有的空格、大小写、单位、换行（例如 `CPU usage in 5 seconds: 20%`，别简化成 `CPU 20%`）；
- **一律原样给全，不要省略、概括、改写**。不要只挑"与判定相关"的几行，也不要写成
  "登录 banner（含 Ubuntu 版本信息、系统信息…）"这种摘要——**摘要丢掉的内容，后面生成
  命令映射时只能靠模型编来补**，而编出来的版本号、IP、时间戳会被误认为是真机回显。
  与判定无关的内容（banner、更新提示、`Last login`）同样照抄，要不要解析留给后面决定；
- **命令与回显里都不要带系统提示符**。写命令就写裸命令（`show version`），不要写
  `Switch> show version`；回显只写设备输出本身，不要带单独的提示符行。原因是**同一个脚本
  要跑在不同设备上，各家提示符都不一样**（`Switch>`、`slot1>`、`(config)#`、`#`、`$` …），
  把某台设备的提示符固化进需求会误导生成的脚本去依赖它。
  注意只剥行首的、或独立成行的提示符；报文正文里本来就有的 `>`（如 `Enter selection>`）
  属于设备输出，要保留。
- **命令没有回显时，必须明确写"该命令无回显（收到空字符串）"**。这一条踩过坑：
  需求里说的是"收到空字符串"，早期实现却把空回显当成"没配置"整条丢弃，命令根本没注册进
  模拟设备，于是返回 `not recognized`，测试环境与被测需求完全不一致，把生成一路带偏。
  现在空字符串是合法回显，但前提是你**明确说出来**。
- **你省略的内容，映射不会替你编，只会留空。** 命令映射里的 `response` 只能逐字取自你的
  描述原文；描述里没给的回显一律留空字符串。所以"写个摘要"的直接后果是测试环境少一段回显，
  脚本解析它就会失败——**摘要不是省事，是埋雷**。

### 3. 处理逻辑——从回显里取什么

说明脚本要提取哪个值、怎么判断。例如"从回显中提取 5 分钟均值"、"按正则匹配 `ZXCTN 9000-`
判断型号"、"状态文案为 `skipped` 时视为跳过而不是失败"。

边界口径要在这里讲清：大小写是否敏感、值缺失时算失败还是跳过、多行报文取哪一行。

### 4. 预期——给出可判定的标准

写"通过的标准是什么"，含阈值与边界。不要写"正常""合理""健康"这类没有判据的词。

- 差：`CPU 利用率不能太高`
- 好：`CPU 5 分钟均值 < 70% 判通过；>= 70% 判失败并给出实测值`

数值的边界、单位换算（百分比、毫秒、dBm）都要写。评估只能按你给的口径判，你没给口径，
它就只能归因成"需求不明确"或"需要用户确认"。

### 5. 需要记录的字段，以及它的来源

如果你的需求要求脚本记录某些字段（网元名称、站点、机房、业务名等），**必须说清这个值从哪来**：

- 来自设备回显：指明是哪条命令回显里的哪一部分；
- 来自平台上下文：可以直接用 `device_config`，但调试环境下它通常只有
  `host / port / username / password / enable_password`；真实执行时才可能多出
  `name / device_model`；
- 平台和设备都拿不到、只有你自己知道：**那就现在写出来**，或者明确说"此项留待确认"。

不说清会有两个后果：脚本被禁止编造，只能把该字段留空并标成 `[待确认]`，
评估据此判不通过并把问题抛回给你——多跑一轮，且结果不算通过。
（反面典型：写死 `网络名称: 默认网络`、拿板卡号当网元名称、把型号当设备地址。
这种"看起来填上了"的假值比留空更糟。）

## 同一命令在不同上下文下回显不同时怎么写

这是树状命令映射要解决的场景：不同单板、不同目录下执行同一条命令，回显不一样。

除了上面五件事，还要额外写清楚：

1. **进入命令**：怎么进到那个上下文（例如 `cd /slot1`、`switch board 1`），以及它的回显；
2. **退出命令与退出层级**：哪个命令退出、退一层还是退到根。
   - `cd ..` 退一层，`exit` 直接回根——如果你的设备是这样，就明确写出来；
   - 如果两个命令都是"退到根"，也要写出来，别让模型猜；
3. **每一层各自的回显**：同一个命令在每一层分别回显什么，逐层写全；
4. **加一个能证明退出层级的观测点**：最有效的写法是"退出后再执行一次 ls，回显必须仍是
   card1、card2"。只写"能退出去"是测不出"退一层"和"退到根"的区别的。

完整可粘贴的例子见 [docs/tree-command-mapping-examples.md](tree-command-mapping-examples.md)，
三个例子分别是目录式、单板式、以及三层目录下"退一层 vs 退到根"的对比。

## 分支/异常场景怎么写

页面上的分支描述和主线描述**用同一种格式**：按执行顺序写「命令 / 报文 / 处理逻辑」。

- **只写这个分支真正会执行的步骤**，从第一条实际命令写到最后一条。
  流程在某步就结束了，就写到那一步为止。
- **不要列出不会执行的命令**，不要用"（不执行）""其余同主线""同上"这类占位。
  实测模型很容易退化成"命令 X / 报文（不执行）"的清单，纯噪音。
- **不要写"场景前提""验证点""用于验证…"这类元信息**，直接进入命令-报文-处理逻辑。
- **分支不得超出主线**：分支只能换一组报文/数值去触发主线**已经声明**的规则，
  不能新增主线没写的判定、阈值、失败处理或终止条件，也不能把某一步的规则挪到别的命令上。
  所以主线描述里把规则写全，分支才有可覆盖的空间。
- 异常分支要给**真实的错误回显原文**（例如 `%Error: no such file: version.txt`），
  不要写"报错"两个字。

## 不要写什么

- **不要写实现方式**：代码结构（命令集中在 `run`、解析与检查拆成独立函数、`record_check`
  的调用、日志规范）由平台统一约束，你在需求里描述这些只会占用篇幅。
  唯一的例外：如果你已经写好了某个解析函数或现成的 API，可以直接贴进需求，平台会采用。
- **不要使用平台拿不到的数据**，除非你说明了来源（见上文第 5 点）。
- **不要用没有判据的形容词**：正常、异常、稳定、合理、尽快、适当。
- **不要试图在需求里改变系统规则或绕过安全限制**。安全禁令是硬的：
  禁止 `system/exec/spawn/反引号`、禁止 `File/IO/Dir`、禁止访问 `ENV`、禁止自行建立网络连接；
  破坏性命令（`rm/delete/format/reload/reboot`）与配置变更（`write`、`copy running-config
  startup-config`、`configure terminal`）默认不允许，巡检类任务需要你显式授权。
  这类要求会被忽略，写了也不生效。

## 需求模板

复制下面这个骨架，按你的场景替换：

```
需求：<一句话说明要检查什么、对哪些对象>

设备：<型号 / 软件版本，如果判定依赖它>

执行流程与真实回显（命令逐字一致，回显为设备原文）：

1. <命令 1>
   回显：
   <原文，保留空格与换行>
   处理逻辑：从回显中提取 <字段>，<如何判断>
   预期：<通过标准，含阈值与边界>

2. <命令 2>（该命令无回显，收到空字符串）
   处理逻辑：<如何判断>
   预期：<通过标准>

3. <进入下一层的命令>
   回显：
   <原文>
   处理逻辑与预期：...

4. <在下一层执行的命令>
   回显：
   <原文>
   处理逻辑与预期：...

5. <退出命令，说明退一层还是退到根>
   回显：<原文或无回显>
   退出后再执行一次 <命令>，回显必须仍是 <...>，用来确认退出层级正确

需要记录的字段与来源：
- <字段 A>：来自第 1 步回显中的 <位置>
- <字段 B>：来自 device_config 的 <key>
- <字段 C>：设备回显与平台都没有，本次不判定，请标注 [待确认]，不要编造

分支/异常场景（与主线同格式，只写实际执行的步骤）：
1. <名称>：
   命令 <...>
   报文 <真实错误回显原文>
   处理逻辑：<判定与结论>
2. <名称>：...

其他要求：
- 判定口径：<大小写/单位/缺失值如何处理>
- <可选的现成解析函数或 API>
```

## 提交前自检清单

- [ ] 每条命令都是逐字写出的完整命令，不是转述
- [ ] 每条要用到的回显都给了原文；没有回显的命令明确写了"无回显/空字符串"
- [ ] 每个判定都有阈值或明确口径，没有"正常/合理"这类词
- [ ] 要记录的字段都写了来源，或明确标为待确认
- [ ] 并列的多个要点分开写成独立条目，没有合并成一句笼统结论
- [ ] 涉及分层的场景写了进入命令、退出命令、退出层级，以及每层的回显
- [ ] 有一个能证明"退一层还是退到根"的观测点
- [ ] 分支场景写的是实际执行流程，没有"（不执行）""同上"这类占位
- [ ] 分支没有引入主线未声明的规则或阈值
- [ ] 没有依赖调试环境拿不到的字段（`device_config` 调试期只有 host/port/username/password/enable_password）
- [ ] 没有在需求里描述代码结构，也没有试图绕过安全限制

## 被退回或反复重试时怎么改

平台跑完一轮后，如果判定不通过，会给出下面几类信息，对症补描述即可：

| 平台反馈 | 说明 | 你该怎么改 |
|---|---|---|
| `needs_user_confirmation` + 需要确认的问题 | 某条目依赖的信息，需求、回显、平台上下文里都没有 | 把该信息补进需求，或指定来源 |
| `env_mismatch` + `mapping_suggestions` | 模拟设备回放的报文与你的描述不一致 | 检查该命令的回显原文是否写全、是否改写过空格/大小写；空回显是否写明 |
| `requirement_ambiguity` | 需求本身描述不清，无法判断 | 补判定口径与阈值 |
| `script_issue` | 脚本逻辑、解析或遗漏 | 若确认是描述导致的，把处理逻辑写得更明确 |

另外两点值得知道：

- **生成阶段最多重试 3 次**，评估不通过则带着失败原因进入下一轮。需求自相矛盾或缺少判据时，
  三轮往往都会失败，最后仍需你补充信息——与其等它空转，不如一开始就写全。
- **评估只会依据本次需求描述拆条目**，不会因为描述之外的代码问题判你不通过。
  所以别把"顺手也看看 XX"写进需求：那会变成一条必须通过的条目。

## 附：手工日志 + 目标 → 需求框架（页面「从手工日志生成」的输入示例）

页面需求描述旁边的「从手工日志生成」按钮，接受**一句目标**加**一段手工操作终端的原始记录**，
由 AI 按本指南的骨架整理成需求描述。适合你已经在设备上手工做过一遍、懒得再逐条誊写命令和回显的场景。

### 目标

```
巡检这台传输设备的配置文件与硬件状态，输出一份可复核的巡检结论
```

### 手工操作日志（原样粘贴，不用整理）

```
ZXCTN 5.170 (R) software, Version 5.170.20
Copyright (c) 2020 ZTE Corporation

Login: admin
Password:

Switch> terminal length 0
Switch> show version
ZXCTN 5.170 (R) software, Version 5.170.20
Copyright (c) 2020 ZTE Corporation
Switch> cd /slot1
slot1> ls
config.dat
license.txt
version.txt
slot1> cat version.txt
V5.170.20
slot1> cls
%Error: unknown command 'cls'
slot1> ls
config.dat
license.txt
version.txt
slot1> cd ..
Switch> cd /slot2
slot2> ls
config.dat
alarm.log
slot2> cat version.txt
%Error: no such file: version.txt
slot2> cd ..
Switch> show fan
Fan 1: Normal
Fan 2: Fault
Fan 3: Normal
Switch> show fan
Fan 1: Normal
Fan 2: Fault
Fan 3: Normal
Switch> show power
Power 1: Normal
Power 2: Normal
Switch>
```

### 这段日志里故意埋了四类噪音

它们分别对应提示词里的清洗规则，不需要你手工删：

| 日志里的内容 | 应被如何处理 |
|---|---|
| `ZXCTN ... Copyright` 横幅、欢迎信息、`Last login` 等 | **原样写进框架**（是设备输出，禁止概括成"登录 banner（含…）"） |
| `Login:` / `Password:` 提示 | **剥离**（登录交互提示，既不是命令也不是输出） |
| 行首的 `Switch>`、`slot1>`，以及输出后单独成行的提示符 | **剥离**：命令只留裸命令、回显只留设备输出（提示符因设备而异，不能固化） |
| `terminal length 0` | **也算一个步骤**：日志里出现的命令都算，回显为空就写"无回显（收到空字符串）" |
| `slot1> cls` 报 unknown command | 敲错重来，忽略这条；以随后成功的 `ls` 为准 |
| `show fan` 连执行两次 | 重复执行，只保留一次 |

### AI 大概率会留出的待确认项（每项最多两个候选）

日志里只有"事实"，没有"判据"，所以下面这些它**不应该**替你拍板，而是给候选让你选或自己写：

- `show fan` 里 Fan 2 是 Fault——**这算故障还是已知现象？** 候选可能是"故障，巡检判失败" / "已知现象，记录但不判失败"。
- 配置文件齐全的判据是什么？/slot2 缺 `version.txt` 算不算不合格？候选可能是"必须含 config.dat 与 version.txt" / "只要求含 config.dat"。
- 版本号是否要与基线比对？基线是多少？这一项日志里完全没有，通常连候选都给不出（推不出就给 0 个，由你自己填）。
- 巡检结论里要不要写网元名称？它从哪来（日志里没有，`device_config` 调试期也只有 host/port）？

### 日志里出现的每条命令都算一个步骤

不要替平台判断"这条看起来不是业务命令，可以省掉"。日志里出现过的命令——登录/建连
（`ssh xxx`）、进入容器（`docker exec ... /bin/sh`）、切目录（`cd`）、`terminal length 0`
这类终端设置——**都是脚本实际要下发的一部分**，都要写成步骤，回显为空就写"无回显"。

只有两类东西不算步骤：**终端自己回显的提示符**（`zb@localhost:~$`、`root@host:~#`、
`Switch>`、`#`，以及 `Login:`/`Password:` 这类登录交互提示），和**敲错重来/重复执行**的那几次
（清洗时按最终成功的那次保留）。

**这些步骤默认全部由脚本下发**，包括登录建连、进入容器、切目录、终端设置。只有你**明确写了**
某条不需要脚本执行（例如注明"该步骤由环境预先完成"），平台才会跳过它。所以：

- 如果你不希望脚本发某条命令，别指望它自己猜，**在描述里写明**；
- 反过来，凡是日志里做过、你又想复现的动作，交给它就一定会下发——包括 `ssh`、`docker exec`。

### 框架里的步骤长什么样

每个步骤以**单独一行**的标记开头，两边各 22 个短横线，中间是序号：

```
----------------------步骤1----------------------
标题：SSH 登录远程主机
命令：`ssh qingyun`
回显：
<设备/主机输出原文，一字不改>
处理逻辑：…
预期：…
```

标记录用固定格式是为了让步骤边界一眼可见，也方便按步骤定位待确认占位符。你手工写需求时不必
用这个格式，但用了它，模型会更容易照着生成。

### 待确认项应该就近写在各步骤里

框架里的待确认占位符（`【待确认#1】`）要写在**它所属那一步的「处理逻辑」或「预期」行内**，
不要堆在框架末尾另起一段清单。两个原因：

- 点候选是把该占位符**就地**替换成选定值。占位符离它管辖的那条命令越近，填的时候越不用
  来回翻；后面生成脚本时，"命令 → 回显 → 判据"也是当整体读的，判据离得远容易挂到别的命令上。
- 页面右侧已经有独立的待确认清单（带候选按钮），那才是汇总视图。框架正文再抄一份，就会出现
  "改了正文忘了末尾"的不一致。

如果生成结果把待确认项汇总到了末尾，把占位符手工挪进对应步骤即可；另外注意右侧清单里有没有
**日志已经能看出来、其实不必问**的项——那类应该直接写成结论。

### 为什么用这段日志

- `/slot1` 与 `/slot2` 下 `ls`、`cat version.txt` 的回显不同，正好触发树状映射（进入 / 退出层级、同名命令分上下文）；
- `cd ..` 能看出退出层级，`cd /slot1`、`cd /slot2` 是对等目录，兄弟层切换不会嵌错；
- 有失败回显（`no such file`）可作为分支场景；
- 全文 43 行、717 字符，远低于 40000 字符上限。

日志粘贴区下方已注明要先删除密码、IP、SNMP 社区串等敏感信息（这段示例里的 `Password:` 后面是空的）。

### 复杂示例：后面的命令依赖前面查出来的值

这是最容易翻车的一类需求：先查一个值，后面的命令**用这个值当参数**。

**目标**：

```
定位本次告警涉及的端口，确认它的链路状态与收光功率，判断是否为真故障
```

**手工操作日志**（原样粘贴）：

```
ZXCTN 5.170 (R) software, Version 5.170.20
Copyright (c) 2020 ZTE Corporation

Login: admin
Password:

Switch> show alarm
ALM-1001  slot1/card2  port3  LOS       Major
ALM-2003  slot2       BoardMissing    Minor
Switch> cd /slot1
slot1> cd card2
card2> ls
port1.status
port2.status
port3.status
card2> cat port1.status
up   1000M
card2> cat port2.status
up   1000M
card2> cat port3.status
down 0M
card2> show optical port3
Rx: -30.5 dBm   Tx: -2.0 dBm
card2> exit
slot1> cd ..
Switch> show fan
Fan 1: Normal
Fan 2: Normal
Fan 3: Normal
```

这里的依赖链是：`show alarm` 的回显里有 `port3` → 提取出 `port3` → 用它去 `cat port3.status`
和 `show optical port3`。注意人工操作时把 port1/port2/port3 都看了一遍，但告警已经指明了
`port3`，脚本按结论所需的最短路径走就行（框架生成后你可以自己删掉多余的步骤再应用）。

**预期框架里必须写明的三件事**（缺一样，生成出来的脚本就断了）：

1. 从**哪条命令**的回显里提取——`show alarm`；
2. 提取**什么值**——端口号 `port3`（写清用什么方式认出来，例如匹配 `ALM-... port(\d+)`）；
3. 用在**哪条后续命令**里——`cat port3.status`、`show optical port3`。

这三件事写在**派生步骤的「处理逻辑」行内**，和用它的命令挨在一起。

依赖还会**逐级传递**：A 的回显解析出的值作为 B 的参数，B 的回显里又解析出 C 的参数（例如先
`docker ps` 取容器 ID，再 `docker exec <id> ...`）。链子上每一级都要按上面三件事写清——只写
第一级，后面的命令一样会断。

**对应的映射要写出派生命令的具体形式**：

```json
{
  "commands": [
    { "command": "show alarm", "response": "ALM-1001  slot1/card2  port3  LOS       Major\nALM-2003  slot2       BoardMissing    Minor" },
    { "command": "cd /slot1", "response": "", "children": [
        { "command": "cd card2", "response": "", "children": [
            { "command": "cat port3.status", "response": "down 0M" },
            { "command": "show optical port3", "response": "Rx: -30.5 dBm   Tx: -2.0 dBm" } ] } ] },
    { "command": "show fan", "response": "Fan 1: Normal\nFan 2: Normal\nFan 3: Normal" }
  ]
}
```

**为什么必须是 `show optical port3` 而不能只写 `show optical`**：映射是**逐字精确匹配**的，
没有通配。派生的值在模拟环境里是确定的（回显固定 → 解析结果固定），所以脚本实际下发的那条
命令可以逐条枚举出来，日志里出现过就照抄。

**这个反例我实测过**：映射里只写 `show optical`、漏掉 `show optical port3` 时，脚本下发
`show optical port3` 会直接拿到 `Command 'show optical port3' not recognized.`——调试日志里
看到这句，基本就是这个原因。映射写全的情况下同一套命令序列全部正常（含从子卡回根层执行
`show fan` 的逐级兜底）。
